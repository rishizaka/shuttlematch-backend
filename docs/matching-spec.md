# ランダムマッチング生成ロジック 仕様書

ShuttleMatch のダブルス試合を自動生成する中核ロジックの仕様。
実装は `src/main/java/com/shuttlematch/domain/service/MatchingDomainService.java`。

本書は**今後のQAをAIに委譲するためのリファレンス**を兼ねる。
第7章「保証する性質」と第10章「QAチェックリスト」が自動検証の起点。

---

## 1. 目的

バドミントンサークルのダブルス練習で、参加者を各セット・各コートに公平かつ
体に優しく割り振る。運営者がボタン一つで「試合表」を生成できることを目的とする。

守りたい価値（優先順）:

1. **公平性** — 全員の出場回数・休憩回数をできるだけ均等にする。
2. **身体ケア** — 特定の人が長時間連続でコートに入り続けないようにする。
3. **多様性** — 同じ顔ぶれの休憩・同じコートの組み合わせが固定化しないようにする。
4. **柔軟性** — 途中参加・早退・セット追加に対応し、それまでの流れを引き継ぐ。

---

## 2. 用語

| 用語 | 定義 |
|---|---|
| 参加者 (Participant) | ルームに登録された1人。番号(1始まり、一覧の並び順)で表示される。 |
| プール (pool) | そのセッションの参加者集合(重複排除済み)。 |
| コート (court) | 1面。1コートで4人が同時にプレーする。 |
| セット (set) | 全コートが同時に行う1巡。1セット = コート数分の試合。 |
| 試合 (Match) | 1コート・1セットの単位。4名(pairA 2名 + pairB 2名)で構成。 |
| 休み (rest) | そのセットでどのコートにも入らない参加者。 |
| ユニット (unit) | 出場・休憩を共にする最小単位。自由参加者=1人ユニット、固定ペア=2人ユニット。 |
| 固定ペア (fixed pair) | 常に同じチームで組む2人。事前に運営者が指定する。 |
| 連続出場 (consecutivePlays) | 直近で何セット連続してコートに入っているか。休むと0にリセット。 |

**定数**（実装値）:
- 1試合の人数 `PLAYERS_PER_MATCH = 4`
- デフォルトセット数 `DEFAULT_SET_COUNT = 10`
- 1セットの必要人数 `required = 4 × コート数`
- 最低参加人数 = `required`（コート数×4）未満は生成不可

---

## 3. 入力・出力

### 入力
- `roomId` — ルーム識別子
- `participants` — 参加者IDのリスト（重複は排除される）
- `courtCount` — コート数（1以上）
- `setCount` — セット数（1以上）
- `fixedPairs` — 固定ペアのリスト（空可）
- `random` — 乱数生成器（シード注入で決定的にできる。テスト・再現用）

### 出力
- `MatchSchedule` — `roomId` と `Match` のリスト。
  各 `Match` は `matchNumber`(1始まり連番)・`setNumber`・`courtNumber`・`pairA`・`pairB` を持つ。

### 主なユースケース
| 操作 | メソッド | 概要 |
|---|---|---|
| 新規生成 | `generate` | 全員同条件で `setCount` セットを生成。 |
| セット追加 | `addSets` | 既存スケジュールの末尾に追加。出場実績を引き継ぐ。 |
| 未開始セット再編成 | `replanFuture` | 途中参加・早退を反映し、未開始セットのみ作り直す。 |

## 4. 中核概念

### 4.1 ユニット化
出場者選択・休憩の反復回避は**ユニット単位**で行う。
- 固定ペア（プールに両方居るもの）は 2人1組のユニット。1人が複数ペアに属することはない
  （先に現れたペアを優先）。
- それ以外の参加者は 1人ユニット。
- 固定ペアが無ければ全員が1人ユニット＝従来の個人単位の挙動に縮退する。

### 4.2 1セットの構成
- 各セットは `required = 4 × コート数` 人が出場し、残り `pool - required` 人が休む。
- `pool == required`（例: 8人2コート）の場合、**休みは発生せず全員が毎セット出場**する。

---

## 5. 生成アルゴリズム

各セットについて、以下を順に行う。

### 5.1 出場者選択（優先度）
ユニットを次のキーで昇順ソートし、前方から `required` 人分を出場に選ぶ
（＝後方のユニットが休む）。事前に Fisher-Yates シャッフルして同順位をランダム化する。

1. **出場回数が少ない順**（第1キー・公平性）
   — 出場回数の差は常に最大1に保たれる。
2. **連続出場が少ない順**（第2キー・身体ケア）
   — 出場回数が同じなら、長く連続でコートに入っている人を後方＝休憩に回す。
   直前に休んだ人は連続0で前方＝優先出場になるため、**連続休みも同時に避けられる**。
3. **ランダム**（第3キー）— 上記が同順位ならシャッフル順で決める。

> 端数補正: 固定ペア(2人)ばかりで枠が1余った場合、自由参加者1人を外して
> 未出場の固定ペア1組を入れて人数を合わせる。

### 5.2 公平性（出場回数の均等化）
第1キーが出場回数のため、出場回数・休憩回数は常に±1以内に収束する。
早く休んだ人は出場回数が1少なくなり、次に優先出場して自己補正される。

### 5.3 連続出場の抑制（身体ケア）
連続出場数を追跡し、公平性(±1)を保ったまま長く連続出場している人を優先的に休ませる。
- 出場したら +1、休んだら 0 にリセット。
- 「休みが取れる構成」でのみ有効。休みゼロ構成（`pool == required`）では抑制できない。

### 5.4 休みの多様化（カップリング防止）
直近セットの「休んだメンバーの組」を履歴（recentRest, 窓 = ユニット数-1）として覚え、
同じ休みグループの反復を避ける。反復しそうな場合、公平性・連続休み回避を壊さない範囲で
（同サイズ・同出場回数・直前に休んでいない、を満たす出場ユニットと）入れ替える。

### 5.5 ペア分け・コート割り
- 固定ペアはそのまま `Pair` になる。
- 自由参加者はシャッフルして2人ずつ `Pair` にする。
- 全 `Pair` を Fisher-Yates シャッフルし、コート番号・pairA/pairB へランダムに割り当てる。
- 試合表の表示上はコート内4人をフラットに扱う（**味方ペアは現地で相談して決める**運用）。

### 5.6 固定ペア
- 固定ペアの2人は**常に同じチーム(同じ Pair)で一緒に出場・休憩**する。
- 複数の固定ペア可（1人は最大1ペア）。
- プールに片方しか居ない固定ペアは無効（1人ユニット扱い）。

## 6. セット追加・再編成（状態の引き継ぎ）

`addSets` / `replanFuture` は、それまでのセットの流れを次の状態として引き継ぐ。
これにより境界をまたいでも公平性・身体ケア・多様性が継続する。

| 引き継ぐ状態 | 目的 | 実装 |
|---|---|---|
| 出場回数 (playCount) | 公平性の継続 | `seededPlayCounts` |
| 最終出場セット (lastPlayedSet) | 連続休み回避の継続 | `seededLastPlayedSet` |
| 連続出場数 (consecutivePlays) | 連続出場抑制の継続 | `seededConsecutivePlays` |
| 休みグループ履歴 (recentRest) | 休みの多様化の継続 | `restGroupsOf` を初期履歴にシード |

### 6.1 addSets（末尾に追加）
- 既存の出場回数・連続出場・休みグループ履歴を引き継いで追加分を生成する。
- 途中参加者（未出場）は優先させない。既存の最小出場回数にシードして横入りさせる。

### 6.2 replanFuture（未開始セットの再編成）
- **開始済みセットは履歴として不変**。一切手を加えない。
- 未開始セットは破棄し、開始済みの実績を引き継いで現在の在席者で作り直す。
- 早退者は未開始セットから除外。途中参加者は優先させない（最小回数にシード）。
- 在席人数でコートを埋められない場合、未来のコート数を自動で縮小する
  （`effectiveCourtCount = min(courtCount, pool / 4)`）。埋められないときは確定分のみ残す。
- 合計セット数は元と同じに保つ。

## 7. 保証する性質（不変条件）

**QAはこの一覧を自動検証する。** 「条件」を満たす構成で「保証」が成り立つこと。

| # | 保証 | 条件 |
|---|---|---|
| P1 | 各試合はちょうど4名で、同一試合内に重複はない | 常に |
| P2 | 出場するのは登録参加者のみ | 常に |
| P3 | 試合数 = コート数 × セット数、matchNumber は1始まり連番 | 常に |
| P4 | 出場回数・休憩回数の差（max-min）が1以内 | 常に（休みの有無を問わず） |
| P5 | 誰も2セット連続で休まない | 休みが取れる構成（`pool > required`） |
| P6 | 回避可能な限り長い連続出場を避ける | 休みが取れる構成。目安: 10人2コートで連続出場 ≤ 6 |
| P7 | 同じ休みグループ・同じコート4人組が固定ローテーションしない | 休みが取れる構成、十分なセット数 |
| P8 | 同一シードなら同一スケジュール（決定的） | 同一入力・同一シード |
| P9 | 固定ペアは常に同じチームで一緒に出場・休憩する | 固定ペア指定時、両者がプールに居る |
| P10 | セット追加・再編成後も P4〜P7 が境界をまたいで継続する | 休みが取れる構成 |
| P11 | replan は開始済みセットを保持し、未開始のみ作り直す | 常に |
| P12 | replan で早退者は未開始セットに出ない／途中参加者は優先されない | replan 時 |

## 8. 構造上の限界・非保証（QAで「不具合」と誤検知しないこと）

- **休みゼロ構成**（`pool == required`、例: 8人2コート・4人1コート）では休みが発生せず、
  連続出場 = セット数になる。これは構造上不可避で P5/P6 の対象外。
- **味方ペアの組み合わせの均等性は保証しない**。コート内4人はフラット表示で、
  実際のペアは現地で決める運用のため、pairA/pairB の同一ペア再出現は許容する。
- 公平性は「最終的に±1」を保証するが、生成途中の一瞬に差が広がる実装挙動は問題ではない。
- 休憩の**間隔**（スペーシング）は連続出場抑制により平準化されるが、
  厳密な等間隔は保証しない（乱数と構成に依存）。
- 参加者が `required` 未満のときは例外（生成不可）。

---

## 9. エッジケース

| ケース | 期待挙動 |
|---|---|
| 参加者 < 4×コート数 | `IllegalArgumentException`（生成不可） |
| ちょうど 4×コート数 | 生成可（休みゼロ、全員毎セット出場） |
| setCount ≤ 0 / courtCount ≤ 0 | `IllegalArgumentException` |
| 固定ペアの片方のみプールに居る | そのペアは無効化（1人ユニット扱い） |
| 参加者削除で固定ペアの一方が消える | ドメイン側で当該固定ペアも自動解除（Room 側の責務） |
| replan で在席者が1コート分未満 | 確定済みセットのみ残す |
| replan で在席者が本来のコート数に満たない | コート数を自動縮小して未開始を再編成 |

## 10. QAチェックリスト（AI自動検証用）

生成結果（`MatchSchedule` の matches）に対して、以下を機械的に検証する。
数値目安は「10人2コート」を主対象とし、他構成でも P列の条件で判定する。

### 10.1 静的検証（1スケジュール単位）
- [ ] **P1** 各 setNumber×courtNumber の試合が4名・重複なし
- [ ] **P2** 全出場者が入力 participants に含まれる
- [ ] **P3** `len(matches) == courtCount × setCount`、matchNumber が 1..N の連番
- [ ] **P4** 各参加者の出場回数 max-min ≤ 1、休憩回数 max-min ≤ 1
- [ ] **P5** 連続2セットの両方で休む参加者が0（休みが取れる構成のとき）
- [ ] **P6** 全参加者の最大連続出場が閾値以下（10人2コートなら ≤ 6。一般には
      「休みゼロでなければ setCount 未満で、単発生成と同水準」）
- [ ] **P7** 同一休みグループ・同一コート4人組の再出現が過度でない
      （直近窓での重複が単発生成と同水準）
- [ ] **P9** 固定ペアの2人が全セットで同一試合・同一 Pair、休みも同時

### 10.2 動的検証（複数生成・操作シーケンス）
- [ ] **P8** 同一シードで2回生成 → matches が完全一致
- [ ] **P8'** 異なるシード20通りで P4/P5/P6 が全て成立（性質ベース）
- [ ] **P10** `generate(10)` → `addSets(6)` の結果が `generate(16)` と同水準
      （最大連続出場・休み差・休みグループ重複を比較）
- [ ] **P11** `replanFuture` 後、開始済みセットの matches が不変
- [ ] **P12** 早退者が未開始セットに登場しない／途中参加者が出場回数で優先されない

### 10.3 検証の与え方（推奨手順）
1. ローカル or 本番 API で `POST /api/v1/rooms/quick`（人数・コート数指定）→
   `POST /rooms/{id}/matches/generate`（`matchCount` でセット数調整）で生成。
2. `GET /rooms/{id}/matches` で取得し、番号は participants の並び順を1始まりに写像。
3. 上記チェックを実行。異なる構成（6人1コート・10人2コート・12人2コート・
   8人2コート＝休みゼロ・固定ペアあり）を横断する。
4. 追加・再編成は `POST /rooms/{id}/matches/sets`・`/replan` を挟んで P10〜P12 を確認。

### 10.4 QA自動スクリプト
`scripts/qa_matching.py` が本章の P1〜P12 を複数構成で自動検証しレポートを出力する
（稼働中の backend API を叩く）。

```bash
python3 scripts/qa_matching.py                              # localhost:8080
python3 scripts/qa_matching.py --base http://3.113.92.223:8080   # 本番
python3 scripts/qa_matching.py --trials 5                   # 性質ベースの試行回数
```

- 検証構成: 10人2コート／12人2コート／6人1コート／8人2コート(休みゼロ)／固定ペア。
- 休みゼロ構成では P5/P6/P7 を自動 SKIP（第8章の非保証に対応）。
- P8(決定性)は API でシード固定不可のため SKIP（下記 Java 単体テストで担保）。
- すべて PASS なら終了コード 0、FAIL があれば 1。新しい性質を足すときは本スクリプトと
  下記テストの両方に追加する。

> 参考: 既存の性質ベーステストは
> `src/test/java/com/shuttlematch/domain/service/MatchingDomainServiceTest.java`。
> P4〜P11 に対応するテストが実装済み（新しい性質を追加する際はここに足す）。

## 11. 変更履歴（アルゴリズム上の主な意思決定）

- 休憩ペアの固定ローテーション問題を修正（少人数で同じ2人が繰り返し休む → recentRest 導入）。
- 固定ペア機能を追加（ユニット化）。
- 連続出場の抑制を導入（第2キーを「最終出場セット」→「連続出場数」に変更）。
  10人2コートで最大連続出場が 7〜8 → 5 に改善。
- セット追加・再編成で連続出場数・休みグループ履歴を引き継ぐよう修正
  （境界をまたいだ流れの継続）。
