1. このアプリは何をするのか

バドミントンサークルの運営を支えるバックエンド(サーバー側)です。画面(フロントエンド)は別物で、 ここにあるのは「データを保存し、ルールに従って計算し、JSON で返す」役割のプログラムです。主な機能は2つ:

① 出欠管理 — 誰がいつの活動日(セッション)に参加するかを登録・管理する。

② ダブルスのランダムマッチング — 参加者から「15試合ぶんのペア組み」を、出場回数が公平になるよう自動生成する。

バックエンドとは? ブラウザやスマホアプリ(フロント)から「このセッションの試合を作って」とリクエストが来ると、 計算してデータベースに保存し、結果を返す——その裏方のプログラムです。人が見る画面は持ちません。

3. Java の基礎用語(最低限)

コードを読む前に、最低限これだけ押さえると一気に読めるようになります。

class / クラス
データと処理をひとまとめにした「設計図」。Javaのプログラムはクラスの集まり。
package / パッケージ
クラスを入れるフォルダ。com.shuttlematch.domain.model のようにドット区切りで、実際のフォルダ階層と一致する。
record / レコード
「値を持つだけの不変クラス」を1行で書ける機能(Java 14+)。UserId や Pair がこれ。一度作ったら中身を変えない=安全。
interface / インターフェース
「こういうメソッドを持つ」という約束だけを定義したもの。中身(実装)は別のクラスが書く。DDDで多用される(§5)。
annotation / アノテーション
@RestController のような @ 付きの目印。Springに「これはコントローラだよ」と教える。
メソッド
クラスが持つ「処理」。関数のこと。generate(...) など。
このリポジトリでは record が「値オブジェクト」(後述)に、ふつうの class が「エンティティ」に、 interface が「リポジトリの約束」に、それぞれ使い分けられています。この対応が分かると設計が読めます。

4. Spring Boot とは何者か

Javaで「Webサーバー」を一から作るのは大変です。Spring Boot はその面倒をほぼ全部肩代わりしてくれる土台です。 このアプリの入口はたった14行:

@SpringBootApplication
public class ShuttlematchApplication {
    public static void main(String[] args) {
        SpringApplication.run(ShuttlematchApplication.class, args);
    }
}

この main を実行すると、Spring Bootが裏で:

  • Webサーバー(Tomcat)を起動して 8080番ポートで待ち受ける
  • @RestController の付いたクラスを自動で見つけてURLと結びつける
  • DBに接続し、Flywayでテーブルを用意する
DI(依存性の注入) —— Springの最重要概念。「このクラスが動くには別のクラスが必要」という関係を、Springが自動で組み立ててくれます。 例えば SessionController のコンストラクタは CreateSessionUseCase を引数で受け取りますが、 あなたが new で作る必要はありません。Springが用意して「注入」します。これがコードを疎結合に保つ鍵です。

5. DDD の4層アーキテクチャ

このプロジェクトの最大の特徴は DDD(ドメイン駆動設計)で4つの層に分けていること。 「ビジネスのルール(=ドメイン)」を中心に置き、技術的な都合(DBやWeb)を外側に追いやる考え方です。 上から下へ依存が流れます:

presentation 層 presentation/api

外との窓口。HTTPリクエストを受け、JSONを返す。Controller / Request / Response。

▼ 呼ぶ
application 層 application/usecase

ユースケース(操作の段取り)。「セッションを作る」「試合を生成する」といった処理の流れを組み立てる。

▼ 使う
domain 層 domain/model · service · repository

心臓部。ビジネスルールそのもの。Spring にも DB にも依存しない、純粋なJava。ここが一番大事。

▲ 実装を提供(interfaceを実装)
infrastructure 層 infrastructure/persistence · config

技術的な詳細。JPAでDBに保存する具体的な処理、設定など。domain層が定義した「約束(interface)」を実装する。

依存の向きがミソ: domain層は他のどの層も知りません(Springすら import しない)。 逆に外側の層が domain を頼ります。こうすると「DBをPostgreSQLからMySQLに変えても、ルールのコードは1行も変えなくていい」という強さが生まれます。 これがなぜわざわざ層を分けるのかの答えです。

7. 1リクエストが流れる様子

「セッションを作る」リクエストを例に、4層をデータがどう通り抜けるか追ってみましょう。

📱 クライアント
POST /api/v1/circles/{id}/sessions → 🔵 SessionController
JSONを受け取る → 🟢 CreateSessionUseCase

コントローラの実コードを見ると、この「受けて → ユースケースに渡して → レスポンスに変換」という薄さがよく分かります:

@PostMapping("/api/v1/circles/{circleId}/sessions")
@ResponseStatus(HttpStatus.CREATED)
public SessionResponse create(
        @PathVariable UUID circleId,
        @Valid @RequestBody CreateSessionRequest request) {
    CreateSessionCommand command = new CreateSessionCommand(...);
    Session session = createSessionUseCase.execute(command);  // 段取りは丸投げ
    return SessionResponse.from(session);                     // ドメイン→JSON用に変換
}
アノテーション意味
@PostMappingこのURLにPOSTが来たらこのメソッドを呼ぶ
@PathVariableURLの {circleId} 部分を引数として受け取る
@RequestBodyリクエストのJSON本文をJavaオブジェクトに変換
@Valid受け取ったデータが妥当か(必須項目があるか等)を自動チェック
@ResponseStatus(CREATED)成功時にHTTPステータス201を返す

8. ドメインモデルの中身

DDDでは登場人物を3種類に分けます。このリポジトリの実例で見ましょう。

① 値オブジェクト(Value Object)— record

「値そのものに意味があり、変わらない」もの。IDや組み合わせなど。例: UserId は「ただのUUID」ではなく「ユーザーのID」という意味を型に持たせています。

public record UserId(UUID value) {
    public UserId {
        Objects.requireNonNull(value, "UserId は null にできません");
    }
}
Pair が秀逸な例: ダブルスのペアは「AとB」も「BとA」も同じはず。 そこで生成時にUUIDを昇順に並べ替えて正規化しているので、new Pair(a,b) と new Pair(b,a) が equals になります。 「同じペアかどうか」の判定をルールとして型に閉じ込めているわけです。

② エンティティ / 集約ルート(Aggregate Root)— class

「IDで識別され、状態が変化する」もの。Session はその代表で、集約ルート(=関連するデータの取りまとめ役)です。 参加者リストを抱え、参加登録のルールを自分で守ります:

public Participant addUser(UserId userId) {
    ensureCanModifyParticipants();          // 受付中以外は拒否
    if (already) throw new IllegalArgumentException("既に参加しています");
    ensureCapacityAvailable();               // 定員チェック
    Participant participant = Participant.ofUser(userId);
    participants.add(participant);
    return participant;
}
なぜここにルールを書く? 「定員オーバーは禁止」「重複参加は禁止」といったルールを Controllerやデータベースではなく Sessionクラス自身 に持たせます。こうすると、どこから呼ばれても必ずルールが守られ、 ルールの置き場所が散らばりません。これがDDDの「ドメインを中心に」の実践です。 コンストラクタが private で、生成は Session.create(...) という名前付きメソッド経由なのも、 「正しい状態でしか作れない」ようにする工夫です。

③ リポジトリ(Repository)— interface

「集約をDBに保存・取得する」約束。domain層にはinterface(約束)だけを置き、実際のDB処理(JPA)はinfrastructure層の ...RepositoryAdapter が実装します。 これが §5 の「依存の向き」を実現する仕掛けです。

9. マッチングのアルゴリズム

このアプリの目玉、MatchingDomainService。「15試合ぶんのダブルスの組み合わせを、なるべく公平に」生成します。 ロジックの方針は3つ:

① 出場回数が少ない人を優先 — 毎試合、これまでの出場回数が少ない順に4人を選ぶ。結果として全員の出場回数が均等になり、奇数人数でも自然に「待ち番」が回る。

② Fisher-Yates シャッフルでランダム化 — 同じ出場回数の人どうしの順番決めと、4人を2ペアに分ける部分をランダムに。

③ 同じカードの連続を回避 — 直前の試合と全く同じペア対戦になりそうなら、数回まで組み替えを試す(ベストエフォート)。

for (int number = 1; number <= matchCount; number++) {
    List<ParticipantId> four = pickLeastPlayed(pool, playCount);  // ①出場少ない順
    Match match = buildMatch(number, four, previousCard);          // ②③ペア分け
    matches.add(match);
    previousCard = match.pairs();
    four.forEach(p -> playCount.merge(p, 1, Integer::sum));        // 出場回数を+1
}
テストしやすい設計: 乱数生成器をコンストラクタで外から渡せる(new MatchingDomainService(random))ようになっています。 テストでは「シードを固定した乱数」を渡せば毎回同じ結果になり、ランダムなのに検証可能。これも「外から依存を注入する」DIの考え方です。

定数で挙動が決まっているのも読みやすいポイント: MIN_PARTICIPANTS = 4(最低4人)、DEFAULT_MATCH_COUNT = 15(標準15試合)。

12. 用語集

JPA
Javaオブジェクトとデータベースの表を対応づける仕組み。@Entity の付いたクラス(SessionEntity 等)がDBの1行に対応する。
Entity (JPA) vs Entity (DDD)
紛らわしいが別物。JPAのEntityはDB保存用の入れ物(infrastructure層)。DDDのEntityはルールを持つドメインの主役(domain層の Session 等)。このリポジトリは両者を意図的に分けている。
DTO
Data Transfer Object。層をまたいでデータを運ぶためだけの入れ物。Request/Response/Command など。
UseCase
「1つの操作」の段取りを表すクラス。例: CreateSessionUseCase.execute()。コントローラを薄く、ドメインを純粋に保つ緩衝材。
CORS
別ドメインのフロントからこのAPIを呼べるようにする許可設定。CorsConfig にある。
Lombok
@Getter 等のアノテーションで定型コードを自動生成するライブラリ。build.gradle.kts に登場。
Flyway migration
V1__init.sql のような連番ファイルでDBスキーマを管理。アプリ起動時に未適用のものを順に実行する。
actuator
アプリの健康状態などを /actuator/health で公開するSpringの機能。
